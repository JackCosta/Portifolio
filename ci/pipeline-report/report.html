2. Como o pipeline funciona

O workflow .github/workflows/ci.yml roda a cada push (qualquer branch), em pull requests, diariamente às 06:00 (para detectar mudanças nas aplicações públicas) e sob demanda. Um commit novo na mesma branch cancela a execução anterior (concurrency).

Quality gate
  • Falha rápida e barata: o estágio de qualidade (lint, tipos, compilação e validação do script k6) roda antes de qualquer teste.
  • Paralelismo: API, E2E e mobile rodam ao mesmo tempo; Playwright usa uma matriz com um job por navegador e dispositivo.
  • Reaproveitamento: três workflows reutilizáveis (Cypress, Rest Assured e Playwright) e uma action composta para projetos Node evitam passos duplicados.
  • Cache: dependências npm e Maven, binário do Cypress e navegadores do Playwright.
  • Dependência lógica: a performance só roda se os testes funcionais de API passarem.
  • Defeitos conhecidos: os cenários @bug rodam em jobs separados e não bloqueantes, gerando evidências sem esconder regressões reais.
  • Segurança: credenciais via secrets, URLs via vars, permissão mínima (contents: read) e entradas passadas por variável de ambiente.
  • Rastreabilidade: cada job publica relatórios e evidências como artefato; o job final gera este relatório em Markdown, HTML e PDF e aplica o quality gate.

8. Mobile: cobertura atual e próximo passo

O estágio mobile executa a suíte E2E do SauceDemo emulando dispositivos reais no Playwright: Pixel 7 (Android, Chrome) e iPhone 15 (iOS, Safari/WebKit), com viewport, densidade de pixels, user agent e eventos de toque de cada aparelho. Isso cobre a experiência web mobile.

O portfólio não tem um aplicativo nativo. Quando houver, o estágio mobile recebe um job com Appium (ou Maestro) em um emulador Android (reactivecircus/android-emulator-runner) e, para iOS, um runner macos-latest com simulador, ou um device farm (BrowserStack, Sauce Labs, AWS Device Farm). Ele entra na mesma matriz e publica os resultados como artefato results-mobile-*, que este relatório já consolida.
